# 철거의정석 마케팅 ERP 설계서

> 대상: 철거의정석(철거 플랫폼) 마케팅 조직 — 대표 · 팀장 · 대리
> 목적: 카톡 보고를 없애고, **ERP 입력 → 제출 한 번 → 담당자에게 디스코드/텔레그램 알림**이 가는 업무 보고 체계를 만든다.
> 함께 보기: `erp/index.html` (클릭해 볼 수 있는 프로토타입, 제출 시 실제 디스코드·텔레그램 발송 포함)

---

## 1. 한 장 요약

| 항목 | 결정 |
|---|---|
| 핵심 흐름 | 업무 배정 → 담당자 수행 → **보고 제출(템플릿)** → 검토자에게 알림 → 승인/반려 → 담당자에게 알림 |
| 소통 채널 | **디스코드를 기본**으로 추천. 텔레그램은 모바일 푸시용 보조 채널(둘 다 붙일 수 있게 어댑터 구조) |
| 실시간 대시보드 | DB 변경을 브라우저에 즉시 밀어주는 Realtime 구독 (새로고침 없이 갱신) |
| 역할 | 대표(전체 감독·설정), 팀장(배정·검토), 대리(수행·보고) |
| 1단계 범위(MVP, 2주) | 할 일 + 템플릿 보고 제출 + 디스코드 단방향 알림 + 실시간 대시보드 + 출퇴근 |
| 기술 스택 | Next.js + Supabase(Postgres·Auth·Realtime·Edge Functions) + Discord Webhook/Bot |
| 운영 원칙 | "보고는 ERP에서만, 카톡은 긴급 전화 대용". 알림은 근무시간 안에 묶어서 발송 |

---

## 2. 지금 무엇이 문제인가 → ERP가 바꾸는 것

| 카톡 보고의 문제 | ERP에서의 해결 |
|---|---|
| 보고 형식이 매번 달라 "뭘 했다는 건지" 다시 물어봐야 함 | 업무 유형별 **보고 템플릿** (블로그 발행이면 키워드·URL·형태소 검증 여부가 필수 입력) |
| 대화 속에 묻혀 나중에 못 찾음 | 업무 단위로 보고·검토·댓글이 한 스레드에 쌓임. 검색 가능 |
| 누가 어디까지 했는지 대표가 실시간으로 모름 | 대시보드에 **검토 대기 / 진행 중 / 지연** 이 실시간 집계 |
| 확인했는지 안 했는지 모름 | 검토자가 승인/반려를 눌러야 종료. 디스코드에서 ✅ 반응만 눌러도 "확인됨" 처리(3단계) |
| 마감 관리가 안 됨 | 마감 전날·당일 아침 자동 알림, 지연 건은 팀장·대표에게 요약 |

## 4. 핵심 흐름: 제출 한 번으로 끝나는 보고

```
[대리]  할 일 카드에서 "제출" 클릭
          └─ 업무 유형에 맞는 템플릿 입력 + 최종 의견 한 줄 + 링크/첨부
          └─ 저장 → 업무 상태 = 검토 요청
                 │
                 ▼ (Edge Function, 1초 이내)
[알림 라우터]  "누구에게, 어느 채널로" 규칙 조회
          └─ 검토자(배정자) 멘션 + 우선순위 높음이면 대표도 멘션
          └─ 디스코드 #보고 채널에 임베드 메시지, 업무별 스레드 생성
          └─ (선택) 텔레그램 담당자에게 동일 내용 푸시
                 │
                 ▼
[팀장]  디스코드 알림 클릭 → ERP 상세 → 승인 / 반려(사유)
          └─ 결과가 담당자에게 다시 알림
          └─ 대시보드는 Realtime으로 즉시 갱신 (모든 사람 화면)
```

### 4-1. 업무 유형별 보고 템플릿 (이게 "명확한 보고"의 핵심)

| 유형 | 필수 입력 | 자동 검증/표시 |
|---|---|---|
| 블로그 발행 | 메인 키워드, 발행 URL, 글자수, 사진 수, 형태소 빈도 검증 여부 | URL 형식, 글자수 1,500 이상 경고 |
| 키워드 순위 체크 | 체크 키워드 수, 상승/하락 건수, 특이사항 | 전일 대비 변동 표 자동 첨부(3단계) |
| 플레이스·리뷰 관리 | 플랫폼, 처리 건수, 이슈 | – |
| 광고 운영 | 채널(파워링크/당근/메타), 지출액, 문의 수 | 문의당 비용 자동 계산 |
| 문의 응대 | 문의 건, 변경된 단계, 다음 액션·날짜 | 문의 파이프라인과 연동 |
| 현장 자료 수집 | 현장명, 사진 수, 드라이브 링크 | 블로그 소재함에 자동 등록 |
| 기타 | 최종 의견 한 줄 | – |

모든 유형 공통: **최종 의견 한 줄**(어떻게 처리했는지), 링크, 첨부.

### 4-2. 알림 라우팅 규칙

| 이벤트 | 받는 사람 | 디스코드 | 텔레그램 |
|---|---|---|---|
| 업무 배정됨 | 담당자 | #업무 채널 + 멘션 | 담당자 개인 푸시 |
| 보고 제출됨 | 배정자(검토자), 우선순위 높음이면 대표 | #보고 채널 임베드 + 업무 스레드 | 검토자 푸시 |
| 승인 / 반려 | 담당자 | 해당 업무 스레드 | 담당자 푸시 |
| 댓글 | 업무 관련자 전원 | 해당 업무 스레드 | – |
| 새 문의 인입(홈페이지 폼) | 담당 대리 + 대표 | #문의 채널 | 담당자 푸시 |
| 문의 단계 변경 | 팀장 | #문의 채널 | – |
| 마감 임박(D-1, 당일 09:00) | 담당자 | 개인 DM | 개인 푸시 |
| 지연 요약(매일 09:10) | 팀장, 대표 | #보고 채널 | 대표 푸시 |
| 하루 마감 리포트(18:30) | 대표 | 개인 DM | 대표 푸시 |
| 출근 / 퇴근 | – | #출퇴근 채널 로그 | – |

알림 피로 방지: 같은 사람에게 5분 안에 여러 알림이 생기면 하나로 묶고, 근무시간(08:00–20:00) 밖 알림은 다음 날 아침으로 미룬다(긴급 문의 제외).

## 5. 왜 디스코드를 기본으로 추천하는가

| 기준 | 디스코드 | 텔레그램 | 카카오 |
|---|---|---|---|
| 보고를 채널·스레드로 구조화 | ● 채널 + 업무별 스레드 | △ 그룹 토픽만 | ✕ |
| 담당자 지목(멘션) | ● 사용자 ID로 확실 | △ 사용자명 필요 | ✕ |
| 연동 난이도 | 웹훅 URL 하나로 5분 | 봇 토큰 + chat_id, 10분 | 알림톡: 사업자 채널·템플릿 심사 필요, 내부용 부적합 |
| 양방향(반응·답글 → ERP 반영) | ● 봇으로 쉬움 | ● 봇으로 가능 | ✕ |
| 모바일 푸시 신뢰도 | 보통(앱 설치 필요) | ● 매우 좋음 | – |
| 비용 | 무료 | 무료 | 건당 과금 |

결론: **사무실·PC 중심 업무 흐름은 디스코드**, 현장 이동이 잦은 사람은 텔레그램 푸시를 추가로 켜준다. 사용자별로 "디스코드 / 텔레그램 / 둘 다"를 설정에서 고르게 한다.

## 6. 화면 구성 (스크린샷 어드민 구조를 기반으로 재편)

상단 메뉴: **대시보드 · 업무 · 문의 · 마케팅 · 거래처 · 문서 · 설정** + 출근/퇴근 버튼

| 화면 | 내용 |
|---|---|
| 대시보드 | 상단 4개 지표(오늘 할 일, 검토 대기, 지연, 이번 주 문의) → 실시간 활동 타임라인 → 내 할 일(카드에서 바로 제출) → 최근 문의 → 공지 |
| 업무 > 할 일 | 필터(담당자·유형·상태), 카드/리스트, 인라인 제출 |
| 업무 > 검토함 | 팀장·대표용. 검토 요청 건을 승인/반려 |
| 업무 > 일일보고 | 출근 시 오늘 계획 3줄, 퇴근 시 결과·막힌 점. 18:30 대표 리포트의 원천 |
| 업무 > 캘린더 | 마감·발행 일정 |
| 문의(리드) | 파이프라인 칸반: 신규 → 상담 중 → 현장방문 → 견적발송 → 계약 → 종료. 홈페이지 견적 폼이 여기로 자동 인입 |
| 마케팅 | 키워드 순위표(전일 대비), 블로그 발행 캘린더, 광고 지출·문의 수 |
| 거래처 | 협력 철거업체·광고 대행사·현장 목록. 업무·문의에서 연결 |
| 문서 | 매뉴얼, 보고 템플릿, 블로그 SEO 가이드 |
| 설정 | 사용자·역할, **사용자별 디스코드 ID / 텔레그램 chat_id**, 알림 채널(웹훅), 라우팅 규칙, 업무 유형 템플릿 |

## 7. 데이터 모델 (Postgres)

| 테이블 | 주요 컬럼 |
|---|---|
| users | id, name, role(ceo/lead/staff), discord_user_id, telegram_chat_id, notify_channels[], active |
| tasks | id, title, type, assignee_id, assigner_id, client_id, due_date, priority, status(todo/doing/review/done/returned), created_at |
| task_reports | id, task_id, author_id, summary(한 줄), fields(jsonb, 템플릿 값), links[], attachments[], submitted_at |
| report_reviews | id, report_id, reviewer_id, decision(approved/returned), comment, reviewed_at |
| comments | entity_type, entity_id, author_id, body, source(erp/discord), created_at |
| daily_reports | id, user_id, date, plan, result, blockers |
| leads | id, source, name, phone, region, demolition_type, stage, assignee_id, memo, created_at |
| clients | id, name, kind(협력업체/광고주/현장), contact, memo |
| keywords / keyword_ranks | keyword, target_url; (keyword_id, date, rank, checked_by) |
| notices, documents | title, body, pinned, author_id |
| attendance | user_id, date, clock_in, clock_out |
| notifications | id, event, recipient_id, channel, payload, status(pending/sent/failed), attempts, sent_at |
| activity_log | actor_id, action, entity_type, entity_id, created_at — 대시보드 타임라인 원천 |

`notifications`는 **아웃박스 패턴**: 먼저 DB에 적고, 발송 워커가 보내고 상태를 갱신. 디스코드가 잠깐 죽어도 보고가 유실되지 않고 재시도된다.

## 8. 기술 구성

```
브라우저(PC/모바일 PWA)
   │  Next.js (App Router)
   ▼
Supabase
   ├─ Postgres  (위 테이블, Row Level Security로 역할 권한)
   ├─ Auth      (이메일/비밀번호 + 카카오 로그인 선택)
   ├─ Realtime  (tasks·leads·activity_log 변경을 대시보드에 푸시)
   ├─ Storage   (첨부 사진)
   └─ Edge Functions
        ├─ notify-dispatch : notifications 아웃박스 → Discord Webhook / Telegram Bot API
        ├─ lead-intake     : 홈페이지 견적 폼 → leads 인입 + 알림
        └─ cron            : 09:00 마감 알림, 09:10 지연 요약, 18:30 대표 리포트
디스코드 봇(3단계, 작은 서버 1대 또는 Cloudflare Worker)
   └─ ✅ 반응 → 확인 처리, 스레드 답글 → comments 저장
```

선택 이유
- 실시간 대시보드가 핵심 요구인데 Supabase Realtime이 이걸 코드 몇 줄로 해결한다.
- 업무·보고·문의는 관계형 데이터라 Postgres가 맞다(주간 집계, 키워드별 추이).
- 현재 워크스페이스가 Firebase Studio라 Firebase(Firestore + Cloud Functions)로도 동일하게 구성 가능. 집계·리포트가 많아질수록 SQL이 편해서 Supabase를 1순위로 둔다.
- 예상 비용: Supabase Pro 월 $25 + Vercel 무료 + 디스코드 무료 → **월 4만 원 이하**.

## 9. 단계별 로드맵

| 단계 | 기간 | 범위 | 완료 기준 |
|---|---|---|---|
| 1. MVP | 1–2주 | 로그인·역할, 할 일 배정, 템플릿 보고 제출, 승인/반려, 디스코드 단방향 알림, 실시간 대시보드, 출퇴근 | 팀 전원이 1주일간 카톡 없이 보고 |
| 2. 업무 확장 | 3–4주 | 문의 파이프라인 + 홈페이지 폼 연동, 일일보고, 텔레그램 채널, 마감·지연 자동 알림, 거래처/현장 | 대표가 18:30 리포트만 보고 하루 파악 |
| 3. 양방향·자동화 | 5–8주 | 디스코드 ✅ 반응·답글 → ERP 반영, 키워드 순위 자동 수집, 주간 리포트 자동 생성, 모바일 PWA | 검토 응답 시간 중앙값 30분 이내 |

## 10. 운영 규칙 (시스템보다 중요한 것)

1. 업무 보고는 ERP 제출로만 인정한다. 카톡·구두 보고는 "제출 전 상의"로만 쓴다.
2. 검토자는 알림을 받은 뒤 **당일 안에** 승인/반려한다. 반려에는 사유를 반드시 적는다.
3. 최종 의견 한 줄은 "무엇을, 어떻게, 결과가 어땠는지"로 쓴다. 예: "송도 상가 글 발행, 메인 키워드 12회, 사진 8장, 형태소 검증 완료".
4. 알림 채널은 개인이 고른다(디스코드/텔레그램/둘 다). 대신 골랐으면 켜둔다.
5. 매일 18:30 대표 리포트 → 다음 날 아침 10분 스탠드업에서 지연 건만 다룬다.

## 11. 프로토타입 사용법 (`erp/index.html`)

- 파일을 브라우저에서 열면 바로 동작한다(서버 불필요). 데이터는 브라우저 저장소에 보관되며 **탭을 두 개 열면 한쪽에서 제출한 내용이 다른 탭에 즉시 반영**되어 실시간 대시보드를 체험할 수 있다.
- 상단에서 사용자를 바꿔 대표·팀장·대리 시점을 오갈 수 있다.
- 설정 > 알림 채널에 디스코드 웹훅 URL 또는 텔레그램 봇 토큰·chat_id를 넣으면 **제출 버튼이 실제로 메시지를 보낸다**. (프로토타입이라 브라우저에서 직접 호출한다. 실제 서비스에서는 Edge Function이 대신 보내고 토큰은 서버에만 둔다.)
- 디스코드 웹훅 만들기: 서버 설정 → 연동 → 웹후크 → 새 웹후크 → URL 복사.
- 텔레그램 봇 만들기: @BotFather에서 `/newbot` → 토큰 복사. 받을 사람이 봇에게 먼저 아무 메시지나 보낸 뒤 `https://api.telegram.org/bot<토큰>/getUpdates` 에서 chat.id 확인.
